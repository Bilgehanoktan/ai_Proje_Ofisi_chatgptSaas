# J2-R2 — owner mapping proposal (not ratified)

## Decision under review: allocate from the existing run reservation
0195 admission already increases `sample_budgets.outstanding_minor` and creates a run-scoped `sample_reservations` row in the same transaction. 0196L `sample_settlements` only supports `D0_LOCAL_FAILURE_NO_EFFECT` with recognized cost zero. Do not interpret either as an invocation receipt or add a second debit. This experiment selects allocation, not additional reservation. One run can have many invocation allocations; each allocation permanently consumes part of the original pool. Releasing unused invocation balance reduces outstanding and does not re-open run capacity. Whether a run can top up, reuse released capacity or close a partially used pool is for T1/Budget owners; no rule is ratified here.

## Physical owner crosswalk
| Record | Existing source / proposed owner responsibility |
|---|---|
| run pool | `sample_reservations` keyed by tenant/company/environment/run; retain immutable run issuance transaction, amount, currency and issuance budget revision; owner tracks allocated and unallocated amounts under lock |
| admission | `run_admissions` admission_id/request_digest/transaction_ref and `run_heads` complete Runtime scope; never alias admission transaction to reservation or invocation identity |
| invocation membership | Exact R1 `BINDING`; per-invocation allocation revision and reservation transaction distinct from run issuance; full composite scoped FK to run, budget, project and lease references; unique reservation within budget, invocation idempotency key, invocation digest and membership digest within scope |
| receipts | Owner-controlled immutable reservation/consume/usage/reconciliation role records; unique role per membership, globally unique scoped receipt identity; bind transaction, member, source pin, route/profile and amount; use W5-D ReceiptLookup/ReceiptReadback/OwnerReceiptSnapshot and W5-H ReceiptEffectPin only from exact owner readback |
| balance | `sample_budgets` authoritative CAS, not `SUM` alone; store separate original run issuance revision, invocation allocation revision and current budget revision; recognized/released must match known usage |
| transaction roles | Existing T1 head/mutation/fence/event/outbox/audit + required admission/lease/budget roles as applicable; fixture EVENT/OUTBOX/AUDIT placeholders are not the original T1 write set |
| quarantine | Owner durably records UNKNOWN and preserves outstanding; budget-wide HOLD until explicit verified reconciliation. No zero fill, automated retry, fallback or spend. Overrun or conflicting evidence: reject and escalate, not automatic cost rewrite |
| terminal | Original failure-only release must be protected from releasing the entire original reservation after an allocation; this fixture permits close only on a never-allocated pool. A partially used run's remaining capacity requires a separate owner-reviewed close operation, not a reuse of the current settlement writer. |

## Transaction choreography for owner implementation (NOT_RUN)
1. Under existing root → witness → memory → company stream → run/lease/budget lock order, D5 protected reader inside `execute_authority_fenced_transition` establishes exact protected scope and validity through commit; do not acquire an independent lock or create a grant. Lock pool and budget in an owner-agreed order; prove same root and no deadlocks. Current owner revision, full admission and run reservation references must match; old receipt/attempt/lease cannot act as new authorization.
2. Allocate once using permanent economic identity; decrement unallocated run balance and store membership+reservation receipt. Existing budget outstanding does not increase; allocation CAS and full T1 records commit together. Scope and unique constraints must persist through attempts, restore and concurrent writers. Independent owner readback after commit.
3. Consume under original D5/T1 fence, store unique consume receipt and immutable transaction relation; no repeat or external provider invocation by this code. Lost ACK: inspect durable records from an independent read session and compare exact expected identity/roles; absence is HOLD, not retry permission.
4. Record usage from independently verified provider evidence; exact consume pin, route/profile/invocation, measured token counts and actual integer minor units within authorized ceiling. Original W5 accounting and signed receipt reviewers required; fixture uses supplied synthetic ceilings and pins only.
5. Reconcile once with exact usage/consume pin; subtract entire allocation from outstanding, increase recognized by actual, release reserved minus actual. CAS, membership state, receipt, economic identity and T1 roles commit atomically. Do not reopen run capacity by default. No real accounting/settlement allowed here.
6. UNKNOWN preserves outstanding and sticky quarantine; this experiment intentionally has no unlock/resolve method. Owner must specify an independently verified resolution and restore protocol, including existing unknown flags not attributable to this invocation. No derived absence of unknown in the fixture establishes real budget clearance.
7. Use protected read session and RLS from D4; scoped composite constraints, privileges, transaction isolation, restore fencing and independent custody are required separately. No migration executed, no PG endpoint assumed.

## Fixture invariants
For each run: `issued = unallocated + terminal_released + sum(all historical invocation allocations)`. For the single synthetic budget: `outstanding = sum(unallocated) + sum(unreconciled allocations)`, `recognized = sum(reconciled actual)`. Each reconciliation satisfies `allocation = actual + released`; no second charge on allocation. Every fixture command increments one CAS revision and writes three journal roles in the same transaction. The readback checks membership/index/receipt/role coherence but cannot detect a coherent rewrite of the entire DB. Fixture only, single fixed synthetic scope and budget, static owner fields, no real grant, no PostgreSQL/RLS and no independent verification.
