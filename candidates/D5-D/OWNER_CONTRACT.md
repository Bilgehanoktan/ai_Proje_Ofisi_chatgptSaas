Reuse D4-R4 Request/Binding/SessionFacts, D5-INTENT derive_request/full_intent_digest, D5-B IdentityReadback and inspect_at_fence, D5-C insertion point, existing D0IntentAuthority and D0IntentJournal. Existing D0 registry labels are not authenticated identity. Preserve RootPin(record_sha,key_sha,recovery_epoch), original scope/request/transaction and journal identities separately. D4 Binding includes registry, membership, assignment and role revisions/digests, principal, DB role/database/cluster, expiry and active state. Require protected server resolution, full Core Member and exact ORG cross-store join, no client claims, delegation remains proposal-only. Keep witness epoch and recovery epoch separately typed; equality in W5 candidate is not accepted provenance.

## Publication and transaction ordering
Proposed owner contract, not an implementation: one protected publication version binds those owner observations and the retained witness root without changing witness semantics. A publisher must take the SAME existing owner root fence before exposing any IAM/ORG/role change; the current publish() only CASes witness roots and is not that protocol. Do not encode a composite identity hash as record_sha. Use owner-approved durable publication metadata in the existing authority boundary, outside the ordinary product restore set. Its physical representation is open. For cross-store publication require durable pending barrier BEFORE external change, then exact owner readback and finalization of the new version under the same fence. While pending, missing, unknown, partially restored or inconsistent, all new operations HOLD. Crash before/after external mutation or before finalization must retain pending, not reopen stale binding. Independent reconciliation is required; no automatic compensation or retry. A publisher bypassing the shared boundary is not supported and prevents activation. This contract is fail-closed serialization, not a claim of distributed atomic commit.

Order: protected read -> existing run claim -> same root fence/recheck -> witness -> memory -> company stream -> run -> lease -> budget -> (W5 proposed pool/membership locks, owner order pending) -> original coordinator/write-set -> verified commit outcome/close -> release. Do not acquire a second run claim or unlock root before commit outcome. A publication winning before fence acquisition invalidates the retained binding; one waiting behind the fence linearizes after the protected commit outcome. A claim consumed before a failed recheck remains consumed. A publisher invoked concurrently but not yet finalized is not itself proof of effective revocation; immediate out-of-band revocation cannot be claimed safe with this lock protocol.

## Expiry and uncertainty
Recommend strict expiry through database commit linearization, not a pre-COMMIT-only check or implicit grace period. Need trusted clock domain, server-side enforcement at the agreed linearization point and independent evidence. If impossible to prove with actual transport/DB and owner guarantees, keep HOLD. D5-C-R3 reproduced expiry at cursor exit and inside commit; a second precheck alone is insufficient. Distinguish known rollback before commit, committed exact readback, and UNKNOWN/PENDING on lost ACK/crash/ambiguous cleanup. Expiry observed after a possible commit cannot reverse it or authorize retry. Preserve original claims, journal, immutable receipts and external witness custody. Full restore of all local trust stores remains an unresolved limitation.

## W5-J2-R4 handoff
Respect recorded user-directed R4-01..04 choices: allocate from existing pool, explicit per-phase T1 roles, partial close only unused remainder after reconciliation, preserve original run claim plus durable invocation economic identity. Do not implement W5 phase roles, alias hashes, pool, receipt, terminal or budget here. Original claim is a one-shot execution boundary, not a reusable parent capability. Direct second call with same scope but different binding/tx/request is rejected (actual diagnostic). A future parent-child lifecycle must be explicitly reviewed by D5/T1/W5 owners, reference verified original parent/lease/grant/epochs, validate each phase under common root and current protected binding, persist all W5 aliases and phase uniqueness in approved owner transaction, never reopen original claim or permit a historical parent to authorize child effects. W5's proposed phase operations/roles and CAS mapping are not yet canonical; no ordinary STATE_MUTATION masquerade. No bypass, no grant, no provider call. Keep independent acceptance separate.
